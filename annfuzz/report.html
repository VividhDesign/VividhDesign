Vector Search Correctness Audit

Recall benchmarks measure how often an approximate-nearest-neighbour index finds the true neighbours. This audit checks something different: rules no correct index may break, whatever its recall. The same eleven properties ran against seven libraries. 159 checks applied, and 16 failed, in 5 of the 7 libraries.

Every finding was confirmed with a standalone reproduction. The suite passes against an exact brute-force index, so it reports no false positives on a correct implementation.

What failed

Finding 1 · hnswlib, Voyager, USearch 2.x

One NaN vector shows up in unrelated search results

A NaN component makes every distance to that row NaN, and NaN compares false both ways. Graph construction orders candidates by distance, so the row is never judged worse than anything and ends up linked from much of the graph. Embedding pipelines do emit NaN, for example from normalising a zero vector.

hnswlib 0.8.091 / 200

Share of 200 unrelated L2 queries whose top 10 contains the NaN row. PyNNDescent and, after the fix, Strata refuse the row. In USearch 2.x the row also costs other vectors their self-match: 1,000 of 1,000 rows find themselves without it and 694 with it.

Finding 2 · FAISS, USearch 2.x, PyNNDescent

Copies of one vector become impossible to find

Corpora often hold identical embeddings: boilerplate, generated code, repeated chunks. Between copies every distance ties at zero, so neighbour pruning cannot tell them apart, and a new copy can lose every incoming link. The test stores one vector under 200 keys among 800 others and searches for it with k=200 and a beam as wide as the index.

FAISS HNSW175 / 200
USearch 2.26.6130 / 200
PyNNDescent (cosine)74 / 200

In FAISS the copies' neighbour lists point only at one another, so a search that reaches them cannot leave. A query near the duplicated vector asks for 300 results and gets 154, with recall 0.51 against exact search, although the index holds 1,000 vectors. Without the copies, the same query returns all 300.

PyNNDescent root cause: a distance of −1.7 × 10⁻⁷

PyNNDescent's failure looked random: some builds lost most copies, others lost none. The cause turned out to be the sign of a rounding error. For cosine and dot, distances are computed as −log₂⟨x, y⟩ in float32. For identical rows the result should be 0, but rounding can leave it at +2.6 × 10⁻⁷, at exactly 0, or at −1.7 × 10⁻⁷, depending on the vector.

The search graph is the union of forward and reverse edges, built with scipy.sparse.maximum semantics. An edge present in one direction only is compared with an implicit 0, and zero results are dropped. The code already raised exact zeros to machine epsilon so they would survive. A slightly negative distance slipped past that guard, and every one-directional edge between copies was deleted.

- diversified_data[diversified_data == 0.0] = FLOAT32_EPS
+ diversified_data[diversified_data <= 0.0] = FLOAT32_EPS

The 24 builds cover cosine and dot metrics, 64, 384 and 768 dimensions, and 4 seeds each. The 159 library tests include two new regression tests. They pick a vector whose self-distance actually rounds below zero on the machine running them, because fastmath rounding can differ between CPUs.

FAISS root cause: twice the paper's links

At level 0, each HNSW node has room for 2M neighbours. The HNSW paper's Algorithm 1 gives a new point M links and leaves the other M slots for links from points added later. FAISS fills all 2M when the point is added. Copies tie at distance zero, so they never prune one another. Once a group outgrows 2M, every copy's list is therefore all copies, and later points' reverse links lose to the tied copies. The group is left with few or no edges out. Copies whose reverse links all lose have no edges in.

The fix gives M links only to a point that has an exact duplicate among its candidates. Every other point is linked exactly as before, so graphs without duplicates come out byte-identical.

- int M = hnsw.nb_neighbors(level);
+ int M = nb_links_to_add<C>(hnsw, ptdis, pt_id, link_targets, level);
+ // M instead of 2M at level 0, only when a target is an exact duplicate

The code corpus is 13 open-source repositories split at blank lines, as paragraph-aware RAG chunkers do. 17.6% of its chunk vectors are exact duplicates; the largest group is FAISS's own license header, with 759 copies. Giving every point M links would also fix duplicates, but it costs up to 2 points of recall@10 at a fixed efSearch. A group about 30 times the list size still loses copies: 679 of 1,000 are found with M=16, up from 323.

Strata: found and fixed in the audit

Strata, my own C++ vector database, was the only library besides hnswlib to which all 31 checks applied. Its one failure was the NaN row: accepted, then returned in 2 of 200 unrelated queries, costing 34 of 1,000 vectors their self-match. Inserts now validate the whole batch before changing anything. A refused batch leaves the index untouched and never reaches the write-ahead log, and a non-finite query raises an error. Strata now passes all 31 checks, along with its own 40 C++ test cases (155,238 assertions) and 28 Python tests.

Method

  • Each library sits behind a five-call adapter (build, add, search, plus optional delete, roundtrip and search_filtered), so all of them face identical checks on identical data.
  • Distances are checked against brute force after identifying which convention a library reports (squared L2, L2, 1 − cos, chord distance or dot), so a convention difference is never counted as a bug.
  • Inner-product checks use unit-normalised rows, because otherwise a longer vector can outscore a vector's dot product with itself.
  • Recall is never judged against a target. Only correctness invariants are: valid ids, correct distances, deleted entries staying deleted, isolation of bad input, and reachability of every stored entry.
  • Versions: hnswlib 0.8.0, faiss-cpu 1.16.0, voyager 2.2.4, annoy 1.17.3, pynndescent 0.7.0, usearch 2.26.6, Strata 0.2.0. USearch 3.0.0-rc.1 was probed separately, since it shares a module name with 2.x.
